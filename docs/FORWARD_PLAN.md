## P3：安装器残留清理（条件触发）

评估已完成，结论与方案对比见 [安装器跨构建覆盖残留评估](INSTALLER_RESIDUE.md)：机制已确认
（卸载清单构建期静态展开、安装段不预清理、update 模式跳过卸载）。**是否已在正式升级中发生过尚未
证实，也未排除**——v3.2.0 没有 desktop 锁文件，"无移除行"不能作为历史证据；当前安装是清理后的
环境，同样证明不了历史。要判定需比对 v3.3.0 与 v3.4.0 正式安装包的文件清单。

方向采纳方案 A′：用 `NSIS_HOOK_PREINSTALL` 清理 `resources\backend`，当 `_internal` 下仍存在
`analysis-runs` / `analysis-assets` 时跳过。不采纳版本化资源目录（会把小残留放大成整棵旧目录），
文档约束只作为落地前的过渡说明。

**A′ 设计尚不完整**，落地 PR 必须先解决两点：迁移是复制而非移动（`service/paths.py` 明确保留旧源），
跳过条件对这批用户可能永久成立，需在"接受该限制"与"另立安全退役任务"之间取舍；以及
`NSIS_HOOK_PREINSTALL` 执行早于 `CheckIfAppIsRunning`，须自行处理进程退出、删除失败策略，并补一条
"运行中升级后取消"不留半删除状态的回归。

**触发判据**：新旧发布产物清单中出现只属于旧清单的路径。移除依赖、**升级依赖版本**（版本号进入路径
名即可，如 `numpy-2.5.2.dist-info`）、升级 PyInstaller、换 Python 小版本、删改自带资源都可能满足。
届时在同一个 PR 内带上 A′ 及其升级回归。

在判据满足前不排期，也不作为任何版本的发布阻断项。

- 只有实现、测试和对应验收证据全部完成后，任务才能标记为完成。
- 任务完成后从本文档移除，验收证据归档到对应版本清单；本文档只保留未完成的工作。
- 外部服务偶发成功不能替代可复现证据，历史 provider 的成功也不能证明新 provider 兼容。
- 新发现写入本文档对应任务；版本发布细节写入版本清单，历史版本计划不再追加新工作。
- 对涉及 Key、Cookie、OAuth 或远端错误正文的证据只记录脱敏后的结构化信息。
