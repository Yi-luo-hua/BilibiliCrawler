## P2：安装器残留清理（待排期）

评估已完成，结论与方案对比见 [安装器跨构建覆盖残留评估](INSTALLER_RESIDUE.md)：机制已确认
（卸载清单构建期静态展开、安装段不预清理、update 模式跳过卸载），**并且已实测发生过**。比对两个
正式安装包的产物清单，v3.3.0 → v3.4.0 就地升级会留下 3 个 api-ms-win 转发 DLL。根因是构建环境
差异——两版之间依赖锁与 PyInstaller 版本均未变化，因此**无法从声明层预判**，只能比对实际产物清单。
该残留严重度低，但证明机制会自行触发。

方向采纳方案 A′：用 `NSIS_HOOK_PREINSTALL` 清理 `resources\backend`，当 `_internal` 下仍存在
`analysis-runs` / `analysis-assets` 时跳过。不采纳版本化资源目录（会把小残留放大成整棵旧目录），
文档约束只作为落地前的过渡说明。

**A′ 设计尚不完整**，落地 PR 必须先解决两点：迁移是复制而非移动（`service/paths.py` 明确保留旧源），
跳过条件对这批用户可能永久成立，需在"接受该限制"与"另立安全退役任务"之间取舍；以及
`NSIS_HOOK_PREINSTALL` 执行早于 `CheckIfAppIsRunning`，须自行处理进程退出、删除失败策略，并补一条
"运行中升级后取消"不留半删除状态的回归。

**不再是“等触发”**。触发条件已经满足过一次，而且根因是构建环境差异，无法预判、也无法靠“改动时顺带做”
覆盖。合理的排期是下一次动到安装器或发布流程时一并落地；在此之前先用发布说明作过渡。
已落在用户机器上的那 3 个文件不单独处理，A′ 落地后由下一次升级自然清掉。

仍不作为发布阻断项。
