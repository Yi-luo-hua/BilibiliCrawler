# v3.6.0 桌面候选版

本版尚未公开发布。

除桌面端的版本显示与更新检查外，本版还改变了**爬取任务的成功 / 失败判定**，以及分析请求被
provider 拒绝时的处理。这两处会直接改变你看到的任务状态，请先读「爬取结果的完整性」一节。

## 爬取结果的完整性

此前分页请求失败时会被当作「已到最后一页」静默结束，任务显示成功，但结果是被截断的。本版起
区分两种情况：

- **主评论或动态的分页请求失败**：任务判定为失败，并明确提示结果不完整。已经取得的数据不再丢弃
  ——部分评论会写入对应 run 目录（`comments.json` 与 CSV），重启后仍可读取；部分动态保留在当前
  会话中，可直接导出。
- **子评论（回复）拉取失败**：任务照常完成，按警告处理。B 站的回复接口对「该楼已删除 / 评论区
  已关闭」和「被风控限速」返回同样的空响应，无法区分，因此不能据此判定整次爬取失败——大批量
  爬取时一次限速就会让长时间任务白跑。日志与 `manifest.json` 的 `warnings` 会记录有多少条评论
  的回复没拿到，`counts.reply_failures` 给出同一个数字供程序判断；主评论与其余回复完整保留。
  需要补齐时对同一链接重新爬取即可。

其他相关修正：

- 评论跨页重复时按评论 ID 逐条去重，不再按整页判断，重叠分页不会重复计入。
- 「爬取并分析」在爬取失败时不再继续调用 LLM，不会为不完整的数据消耗额度。
- 爬取过程中点击停止，仍然优先判定为「已取消」而不是「失败」，部分结果照常保存。

## 分析报告与图表

- 桌面端导出的分析 Markdown 现在保留**分析当时**的视频来源、UP 主、发布时间与 Run ID，以及可
  匹配的评论署名。此前导出的报告会跟随最近一次爬取变化，分析完再爬别的视频会改写旧报告的来源。
- 主题排行的导出图与桌面端共用同一套标签截断规则，并为数值预留独立宽度，标签与柱体不再重叠。
  截断按字符而非字节进行，emoji 等字符不会被从中间截断。

## Provider 兼容

- 分析请求被 provider 以 HTTP 400/422 拒绝、且对方在 `param` 中指明 `temperature` 时，移除该字段
  重发一次。本仓库固定发送 `temperature` 0.2 / 0.18，指向不支持自定义采样参数的模型（如 OpenAI
  的推理模型）此前是硬失败。降级只发生一次，与已有的 `response_format` 降级共用同一个三次请求
  预算；provider 未指明字段时一律不改请求、不重发。

## 桌面版本显示与更新检查

- 左上角应用名称下显示当前版本，替代原来的「评论 / 动态」。桌面窗口读取安装版本，浏览器预览
  读取 Cargo 项目版本。
- 侧栏提供手动检查更新、更新说明，以及黑色磨砂底、黄色星星与手写字形的 Star 按钮；点击 Star
  打开项目 GitHub 页面，由用户在 GitHub 完成点星。
- 检查 GitHub 最新正式版本；按数字比较版本，不提示降级。
- 有匹配的 Windows x64 安装包时，可在默认浏览器下载安装包。下载后退出应用并运行安装程序完成
  更新；本版不提供静默安装或自动重启。
- 当前任务运行期间禁用安装包下载入口。网络超时、访问限流、无公开版本、安装包尚未上传等情况
  显示明确提示，可重试；失败提示只显示本应用自己的文案，不回显远端响应内容。

更新源为 `Yi-luo-hua/BilibiliCrawler` 的 GitHub Releases。只有名称、版本和下载地址均匹配的已上传
安装包才提供直接下载入口。

## 已知限制

- v3.5.0 及更早版本没有更新检查，只能自行到 Release 页面发现新版本。
- 经 CLIProxyAPI 的 Antigravity 通道出现的 HTTP 400（`status: FAILED_PRECONDITION`）是上游对
  调用方所在区域的限制，与请求参数无关，本版的 `temperature` 降级不针对也不解决该问题。处理方式
  在 CLIProxyAPI 侧（为对应认证配置受支持区域的出口）。

## 构建与验证

Windows x64 NSIS 安装包使用 CPython 3.13.15 和锁定依赖构建。应用版本统一取自
`desktop/src-tauri/Cargo.toml`。

当前包为本地候选产物。自动化检查与构建结果不能代替真实桌面交互、已有安装覆盖升级及用户数据
保留验收；完整验收项见 [v3.6.0 发布准备与验收清单](RELEASE_3.6.0.md)。
